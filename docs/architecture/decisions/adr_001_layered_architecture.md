# ADR-001: 采用四层分层架构

- **状态**: 已采纳
- **日期**: 2026-05-13
- **决策者**: BanSafe Team

---

## 背景

重构前代码散落在 `embedded_src/` 和 `src/` 中，应用逻辑、传感器驱动、算法混杂在一起，缺乏清晰的模块边界和依赖管理。这导致：
- 无法独立测试单一模块
- 换用不同传感器时需要修改大量上层代码
- 新功能开发容易引入跨层调用（如应用层直接访问 I2C 寄存器）

## 决策

采用严格的四层架构：

```
应用层 (app) → 算法与业务层 (algorithm) → HAL ← 驱动层 (drivers)
```

### 核心约束

1. **算法层只调用 HAL 接口**，绝不直接访问驱动层或寄存器
2. **HAL 负责适配驱动**，将具体硬件差异封装为统一接口
3. **驱动层只负责裸机操作**（寄存器读写、协议实现），不包含业务逻辑
4. **应用层只调度和决策**，不直接处理传感器数据

## 后果

### 正面
- 模块可替换性：换用不同加速度计只需修改 HAL 实现和驱动
- 可测试性：算法层可通过 Mock HAL 进行单元测试
- 并行开发：驱动/算法/应用可由不同开发者并行推进

### 负面
- 代码量增加：多了一层 HAL 抽象
- 性能开销：多一次函数调用间接层（在 ESP32-S3 上可忽略不计）
- 学习曲线：新贡献者需要理解分层约束

## 替代方案

| 方案 | 理由 |
|------|------|
| 不分层（原始状态） | 已证明不可维护 |
| 三层（无 HAL） | 算法层直接调驱动，换传感器需改算法 |
| 五层（过细） | ESP32 项目规模不需要过多间接层 |
